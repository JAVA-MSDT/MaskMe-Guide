🔬 Why the gap? The microbenchmark measures only the masking step. In a real request, masking is one of many steps (network, DB, auth, serialization, business logic) — and at 0.08ms it's less than 0.1% of total time.
📏 Per-field cost: ~0.007ms/field — competitive with Jackson (~0.01–0.05ms/field), better than Gson, Hibernate, and ModelMapper. If those libraries were unacceptable at this overhead, the Java ecosystem wouldn't use them.
✅ Bottom line: MaskMe is recommended for 99% of applications. The only exceptions are sub-10ms latency budgets or >10K req/sec hot paths — where hardcoded masking is the right choice.

🧪 Benchmark Methodology — How We Measured

This benchmark follows JMH-style methodology (the OpenJDK standard for Java microbenchmarks). Here's what the code does and how it aligns with community best practices.

🟢 What We Do Right (JMH-Aligned)

PracticeOur ImplementationJMH EquivalentWhy It Matters
Warmup phase 10,000 iterations before measurement @Warmup(iterations=5) Allows JIT (C1/C2 compiler) to optimize hot paths. Without warmup, the first runs include compilation overhead, skewing results.
GC stabilization System.gc() + Thread.sleep(100ms) between warmup and measurement Fork isolation achieves similar Clears garbage from warmup phase so GC pressure during measurement reflects only the measured code.
Per-sample timing System.nanoTime() per iteration, stored in pre-allocated ArrayList @BenchmarkMode(SampleTime) Enables percentile analysis (p95, p99). Pre-allocation avoids ArrayList resize during measurement.
Percentile calculation Sort samples, pick index at 95%/99% JMH's built-in percentile reporting p95/p99 reveal tail latency — more meaningful than averages for production SLAs.
Multi-dimensional metrics Time, memory, CPU (ThreadMXBean), GC (GarbageCollectorMXBean), throughput @BenchmarkMode + profilers A single metric (e.g., time) can be misleading. Measuring 5+ dimensions gives a complete picture.
High iteration count 100,000 measurement iterations Configurable via @Measurement Reduces noise from OS scheduling, background processes, and timer granularity. More samples = more statistical significance.
Same data, same conditions Both approaches benchmark the exact same DTO (11 + 4 fields) @State(Scope.Benchmark) Ensures the comparison is fair — same object graph, same field count, same values.
Multiple scenarios Single condition, multiple conditions, batch, concurrent @Param variations Tests different real-world usage patterns, not just one happy path.
Multi-run averaging 3 measurement runs per scenario, results averaged @Fork(5) with averaging Reduces variance from OS scheduling, thermal throttling, and GC timing. Cuts noise from ±10% to ±2–5%.

🟡 Honest Limitations (vs Full JMH)

LimitationWhat JMH DoesImpact on Our ResultsMitigation
No fork isolation Runs each benchmark in a separate JVM fork JIT profile pollution — optimizations from the hardcoded run may affect the MaskMe run Hardcoded runs first (simpler code), so any JIT bias would favor MaskMe, making our comparison conservative
No Blackhole Blackhole.consume() prevents dead-code elimination JIT could theoretically optimize away unused return values Both MaskMe (reflection + object creation) and hardcoded (record construction) have side effects that prevent DCE in practice
Timer overhead Batch timing avoids per-iteration nanoTime() calls System.nanoTime() adds ~20–30ns per sample (~3% noise on the hardcoded path) Both approaches pay the same timer cost, so the relative comparison remains valid
Single run 5+ forks, averaged Results averaged across 3 measurement runs to reduce variance from OS scheduling and thermal throttling 3-run averaging eliminates most single-run noise. The Live Benchmark lets you run additional times to verify.
Memory approximation Allocation profilers (e.g., -prof gc) totalMemory() - freeMemory() is a snapshot, not precise per-op allocation Useful for relative comparison (both measured the same way), not absolute allocation tracking

🎯 Verdict: Is This Benchmark Trustworthy?

✅ The relative comparison is reliable. Both approaches are measured with the same methodology, same data, same timer overhead. The ~100x gap is consistent and real.
✅ The methodology follows 7 of 8 JMH best practices — warmup, GC stabilization, per-sample timing, percentiles, multi-dimensional metrics, high iteration count, multi-run averaging.
⚠️ Absolute numbers may vary ±2–5% between sessions (no fork isolation). Use the Live Benchmark to verify on your machine.
⚠️ This is a microbenchmark. It measures isolated masking operations, not real application performance. See the Real-World Context section below for why the scary percentages don't translate to production impact.

References: OpenJDK JMH — the Java Microbenchmark Harness, the community standard for Java performance testing. Baeldung JMH Guide — practical introduction to JMH methodology. Aleksey Shipilëv's talks — JMH author's presentations on benchmarking pitfalls.

🌍 Real-World Context — Why the Numbers Are Misleading

The microbenchmark shows ~100x slower per operation. But in a real web request, masking is a tiny fraction of total time.

Typical web request with MaskMe: Total Response Time: 100ms ├─ Network latency: 20ms (20%) ├─ Load balancer: 5ms (5%) ├─ Authentication: 10ms (10%) ├─ Database query: 40ms (40%) ├─ Business logic: 15ms (15%) ├─ JSON serialization: 5ms (5%) ← Jackson: 10 fields └─ MaskMe masking: 0.08ms (0.08%) ← 11 fields + nested
📊 Per-field cost: ~0.007ms/field (0.08ms ÷ 11 fields) — competitive with Jackson (~0.01-0.05ms/field)
📊 Microbenchmark: Hardcoded 0.0008ms vs MaskMe 0.08ms → +9,767% ← scary but isolated
📊 Real application: Hardcoded 99.92ms vs MaskMe 100ms → +0.08% ← actual user impact

📊 The Trade-off

🔴 Microbenchmark: ~100x slower per isolated operation (0.0008ms → 0.08ms)
🟢 Real-world: <0.1% of total request time (0.08ms in a 100ms request)
🟢 Per-field: ~0.007ms — competitive with Jackson, better than Gson/Hibernate
🟡 GC pressure: ~17x more collections — reflection creates more short-lived objects
🟢 Gains: Centralized logic, conditional masking, framework-agnostic, testable
🟢 Bottom line: For 99% of applications, maintainability wins outweigh the overhead
